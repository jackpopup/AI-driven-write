## [개념 설명 파트 1: Context Engineering] 23:00~33:00

### 발화문 -- 2주차 연결 (23:00~26:00)

> 자, 첫 번째 개념. Context Engineering.
>
> 이 단어, 2주차에 들어보셨어요. 기억나시죠? 프롬프트 엔지니어링이 "AI에게 말 잘 거는 기술"이었다면, 컨텍스트 엔지니어링은 "AI에게 맥락을 미리 파일로 세팅해주는 기술"이었잖아요.
>
> 2주차에 CLAUDE.md를 만들었잖아요. "나는 누구고, 이런 걸 만들고 있고, 한국어로 대답해줘." 이렇게 세 줄짜리 인수인계서를 썼어요. 그랬더니 AI가 매번 자기소개를 다시 안 해도 됐죠.
>
> 근데 여기서 질문. 인수인계서 한 장만 있으면 프로젝트가 잘 돌아가나요?
>
> 안 돼요. 인수인계서는 첫 번째 벽돌일 뿐이에요. 진짜 체계적으로 일하려면 뭐가 더 필요하냐면, 업무 매뉴얼도 있어야 하고, 프로젝트가 지금 어디까지 진행됐는지 상태도 알아야 하고, "이건 하지 마"라는 규칙도 있어야 하고, 과거에 뭘 했는지 이력도 알아야 해요.
>
> 이 모든 걸 체계적으로 정리해서 AI에게 주는 것. 이게 Context Engineering이에요.
>
> CLAUDE.md가 인수인계서 한 장이었다면, Context Engineering은 프로젝트 전체 운영 매뉴얼이에요.

### 발화문 -- 핵심 원리 (26:00~30:00)

> 왜 이게 중요하냐. 실감 나는 예를 들어볼게요.
>
> 여러분이 과제를 하면서 이런 경험 하셨을 거예요. "어제 AI한테 같은 말을 했는데 오늘은 다른 결과가 나온다." 경험해보신 분?
>
> 그 원인이 바로 맥락 부족이에요. AI한테 "로그인 기능 추가해줘"라고만 하면, AI는 모릅니다. 지금 프로젝트가 어떤 상태인지. 어떤 기술을 쓰고 있는지. 이전에 뭘 만들었는지. 맥락 없이 그때그때 추측해서 만드니까 결과가 매번 달라지는 거예요.
>
> 반대로, 맥락이 풍부하면? "이 프로젝트는 뉴스 대시보드고, HTML/CSS/JavaScript로 만들었고, 지금 키워드 검색 기능까지 완료했고, 다음에 검색 기록 저장 기능을 추가할 예정이야." 이렇게 맥락을 다 알려주면? AI가 예측 가능하고 일관된 결과를 냅니다.
>
> [화면: Before/After 비교 다이어그램]
>
> ```
> Before (맥락 없음):
>   "로그인 추가해줘" → AI가 매번 다르게 해석 → 결과 들쭉날쭉
>
> After (맥락 있음):
>   CLAUDE.md + 프로젝트 상태 + 규칙 → AI가 정확히 이해 → 일관된 결과
> ```
>
> bkit의 창시자가 이런 말을 했어요. "Automation First, No Guessing, Docs equals Code." 자동화를 우선하고, 추측하지 않고, 문서가 곧 코드다. 이게 bkit의 철학이에요.
>
> 단순히 프롬프트 한 줄 잘 쓰는 게 아니라, 코드, 문서, 설정, 상태, 규칙을 통합해서 AI에게 주면 AI가 추측하지 않고 정확하게 일한다. 이게 Context Engineering입니다.

### 발화문 -- 실감 나는 예시 (30:00~33:00)

> 좀 더 쉽게 말할게요.
>
> 여러분이 새로운 프리랜서 한 명을 프로젝트에 투입한다고 생각해보세요.
>
> 인수인계서 한 장만 주면? "아, 뉴스 대시보드요? 알겠습니다." 하고 대충 만들어요. 근데 기존 팀이 쓰던 규칙이랑 다르게 만들어서 충돌 나고, 결국 다시 해야 해요.
>
> 반면에, 프로젝트 매뉴얼, 지금까지 진행 상황, 코딩 규칙, "이건 하지 마" 목록, 팀원 역할 분담까지 다 정리해서 주면? 프리랜서가 팀에 쑥 녹아들어서 제대로 된 결과를 냅니다.
>
> AI도 똑같아요. 맥락이 많을수록 결과가 좋아지고, 맥락이 없으면 매번 추측해야 하니까 결과가 들쭉날쭉한 거예요.
>
> 그리고 희소식. bkit이 이 맥락 정리를 상당 부분 자동으로 해줍니다. 여러분이 일일이 다 안 적어도 돼요. 이건 실습에서 직접 보여드릴게요.

### 슬라이드 노트

- 2주차 CLAUDE.md (인수인계서) vs 3주차 Context Engineering (전체 운영 매뉴얼) 비교 다이어그램
- Before/After: 맥락 없는 AI vs 맥락 있는 AI 비교 슬라이드
- bkit 3대 철학: "Automation First / No Guessing / Docs = Code" 키워드 슬라이드

## [개념 설명 파트 2: Skills (27개)] 33:00~38:00

### 발화문

> 두 번째 개념. Skills.
>
> bkit 안에 스킬이 27개 들어 있어요. 스킬이 뭐냐. 업무 매뉴얼이에요.
>
> 비유할게요. 회사에 다양한 업무 매뉴얼이 있잖아요. "신입사원 온보딩 매뉴얼", "프로젝트 시작 가이드", "긴급 대응 프로토콜", "코드 리뷰 체크리스트". 상황에 따라 다른 매뉴얼을 꺼내 쓰잖아요.
>
> bkit의 Skills도 마찬가지예요. 상황에 따라 다른 매뉴얼을 꺼내 쓸 수 있어요. 슬래시(/) 하나로 AI에게 "이 방식대로 일해"라고 지시하는 거예요.
>
> [화면: 주요 Skills 소개 슬라이드]
>
> 자주 쓰는 것만 설명할게요.
>
> **/starter.** 새 프로젝트를 처음부터 시작할 때 쓰는 매뉴얼이에요. "새 프로젝트 착수 매뉴얼"인 거죠. 이걸 실행하면 AI가 알아서 프로젝트 기획서를 만들고, 폴더 구조를 설계하고, 첫 번째 코드까지 한 번에 쭉 진행해요. 백지 상태에서 시작할 때 쓰는 스킬이에요.
>
> **/pdca.** 이미 있는 프로젝트에 기능을 추가하거나 개선할 때 쓰는 매뉴얼이에요. Plan → Design → Do → Check → Act. 기획하고, 설계하고, 만들고, 검증하고, 개선하고. 이 다섯 단계를 AI가 체계적으로 밟아줘요. 그냥 "로그인 기능 추가해줘"라고 말하면 AI가 /pdca를 자동으로 실행해요.
>
> 잠깐, 여기서 Check 단계가 중요한데요. AI가 결과물을 스스로 검증하고 "일치율(Match Rate)"을 계산해요. 설계 문서와 실제 만든 것이 얼마나 일치하는지를 점수로 매기는 거예요. 90% 이상이면 자동 완료, 70~89%면 여러분에게 선택권 드리고, 70% 미만이면 자동으로 다시 고쳐요. AI가 스스로 품질 관리를 하는 거예요.
>
> **/code-review.** 코드를 전문가한테 검토 맡기는 매뉴얼이에요. 기자로 치면 기사를 데스크에 넘기는 거예요. 보안 취약점, 성능 문제, 코딩 관례 위반까지 체계적으로 잡아줘요.
>
> **/zero-script-qa.** 테스트 코드 없이 실제 동작으로 품질 검증하는 매뉴얼이에요. "이 기능이 제대로 동작하는지 확인해줘"라고 하면 AI가 시나리오를 설계하고 직접 돌려봐요.
>
> **/plan-plus.** 기획서를 브레인스토밍 방식으로 더 깊이 파는 매뉴얼이에요. 단순 기획이 아니라, 왜 만드는지, 누가 쓰는지, 어떤 문제를 푸는지까지 질문하면서 기획서를 만들어줘요.
>
> [화면: "자연어로도 됩니다" 강조 슬라이드]
>
> 27개를 다 외울 필요 전혀 없어요. 핵심은 이거예요.
>
> 자연어로 시켜도 됩니다.
>
> "로그인 기능 추가해줘" → bkit이 /pdca를 자동 실행해요.
> "새로 만들어줘" → bkit이 /starter를 자동 실행해요.
> "이거 뭐가 문제야?" → bkit이 /code-review를 자동 실행해요.
>
> 여러분이 명령어를 외울 필요 없이, 의도만 말하면 bkit이 알아서 적절한 매뉴얼을 꺼내 쓰는 거예요. 이게 Skills의 핵심입니다.
>
> 오늘 실습에서는 /pdca, 이거 하나만 써볼 겁니다. 이것만 알면 웬만한 건 다 커버돼요.

## [개념 설명 파트 3: Agents (16명)] 38:00~45:00

### 발화문

> 세 번째 개념. Agents. 에이전트. 이게 오늘의 핵심이에요.
>
> bkit 안에 에이전트가 16명 들어 있어요. 16명의 AI 전문가가 각자 역할을 갖고 있어요. Skills가 "매뉴얼"이라면, Agents는 "그 매뉴얼을 실제로 실행하는 전문가들"이에요.
>
> [화면: bkit Agent 16명 구성 슬라이드]
>
> 크게 세 그룹으로 나뉘어요. 대표적인 역할만 소개할게요, 슬라이드에 전체 목록이 있어요.
>
> **전략가 그룹 7명.** 판단하고 설계하는 팀이에요.
>
> CTO Lead. 팀 전체를 총괄하는 기술 책임자예요. "이 기능, 이 방식으로 만드는 게 맞아?"를 판단해요.
>
> Enterprise Expert. 대규모 시스템 설계 전문가예요. 복잡한 아키텍처 결정을 해줘요.
>
> Product Manager. 기획 전문가예요. "이 기능이 왜 필요한지, 누가 쓰는지"를 정리해줘요.
>
> Security Architect. 보안 전문가예요. 코드에 보안 취약점이 없는지 전담으로 잡아줘요.
>
> **실행가 그룹 7명.** 직접 만들고 검증하는 팀이에요.
>
> Frontend Architect. 화면, UI, 사용자 경험을 설계하고 구현하는 전문가예요.
>
> Backend Expert. 서버, 데이터베이스, API를 담당하는 전문가예요.
>
> QA Strategist. 품질 검증 전략을 짜는 전문가예요. "어떻게 테스트할지"를 설계해요.
>
> Code Analyzer. 코드를 정밀하게 분석하는 전문가예요. 오류, 비효율, 코딩 관례 위반을 잡아요.
>
> Gap Detector. 설계한 것과 실제 만들어진 것이 다른 부분을 찾아내는 전문가예요. "계획대로 됐어?"를 확인해요.
>
> **빠른 처리 그룹 2명.** 단순 반복 작업을 빠르게 처리하는 팀이에요. 속도가 중요한 간단한 작업을 빠르게 돌려줘요.
>
> [화면: 편집국 vs AI 팀 비교 슬라이드]
>
> 언론사에 비유하면 이래요.
>
> 편집국장 → CTO Lead. 전체 방향 판단.
> 취재기자 → Backend Expert + Frontend Architect. 실제 만드는 사람들.
> 교열팀장 → Code Analyzer + Gap Detector. 검증하는 사람들.
> 보안담당 → Security Architect. 민감 정보 노출 체크.
> 기획데스크 → Product Manager. "왜 만드는지"를 정의하는 사람.
>
> 기자 한 명이 취재, 교열, 보안 검토, 기획까지 혼자 다 하면 어떻게 될까요? 오타 나고, 팩트 빠지고, 민감 정보 노출되고. 이래서 편집국에 역할 분담이 있는 거잖아요.
>
> AI도 똑같아요. AI 한 명한테 "로그인 만들어줘"라고 하면, 보안은 잘 챙겼는지, 설계대로 만들었는지, 품질은 괜찮은지를 혼자 판단해요. 놓치는 것들이 생겨요.
>
> bkit은 AI에게 이 조직 구조를 만들어주는 거예요. 역할을 나눠서, 각자 전문 영역을 담당하게 하는 거죠.
>
> [화면: /pdca team 실행 화면]
>
> 그리고 이 16명을 한 번에 소환하는 명령어가 있어요.
>
> **/pdca team**
>
> 이 한 마디면 16명이 동시에 일을 시작해요. CTO가 전체를 감독하면서, 기획자가 기획서 만들고, 개발자가 코드 짜고, 교열팀이 검수하고, 보안팀이 점검하고. 병렬로 동시에 돌아갑니다. 순서대로 기다리는 게 아니라, 다 같이 한꺼번에.
>
> 실제 사례가 있어요. 원래 11명이 4주 걸리던 프로젝트를, 사람 4명에 AI 에이전트 16명 붙여서 2주 만에 끝냈어요. 인원 64% 절감, 기간 50% 단축. 이게 "AI에게 팀을 준다"의 실제 효과입니다.
>
> 여러분은 AI 팀원 16명의 팀장이 되는 거예요.

## [개념 설명 파트 4: Hooks] 45:00~50:00

### 발화문

> 네 번째, 마지막 개념. Hooks.
>
> 훅이 뭐냐. AI가 뭔가를 시작하거나 끝낼 때 자동으로 개입하는 장치예요.
>
> 이건 진짜 쉬운 비유가 있어요.
>
> 요즘 워드 프로세서에서 글 쓰면, 맞춤법 틀린 곳에 빨간 밑줄 뜨잖아요. 여러분이 "맞춤법 검사해줘"라고 안 했어요. 글을 쓰는 순간 자동으로 검사가 돌아가는 거죠. 그게 훅이에요.
>
> bkit의 훅도 마찬가지예요. 두 종류가 있어요.
>
> 하나, 자동 훅. bkit이 알아서 감지해서 실행하는 거예요. 예를 들어 여러분이 "인증 기능 추가해줘"라고 하면, bkit이 "이건 새 기능 추가 요청이네"라고 감지해서, 바로 코드를 짜는 게 아니라 "기획서부터 만들자"고 자동으로 PDCA를 시작해요. 여러분이 시키지 않아도.
>
> 또 다른 예. 코드를 다 만들었으면, 자동으로 "설계서랑 코드가 일치하는지" 검사를 돌려요. 이것도 여러분이 "검사해줘"라고 안 했는데 자동으로 해줘요.
>
> 둘, 수동 훅. 이건 여러분이 직접 개입하는 거예요. AI가 작업하고 있는데 "잠깐, 이 방향 아닌데?" 싶으면 ESC를 눌러서 멈추고 방향을 수정할 수 있어요.
>
> 정리하면, 훅은 품질 관리 자동화 시스템이에요. AI가 멋대로 하는 걸 막고, 체계적으로 일하게 하는 안전장치.
>
> 자, 개념 네 가지를 다 봤어요. 정리할게요.
>
> [화면: 4개 개념 정리 슬라이드]
>
> Context Engineering. AI에게 맥락을 체계적으로 주는 기술.
> Skills 27개. 상황별 업무 매뉴얼.
> Agents 16명. 역할이 나뉜 전문가 팀.

### 슬라이드 노트

**화면**: Hooks 비교 슬라이드

```
수동 훅:

| Hooks | 자동 품질 관리 안전장치 | 워드의 자동 맞춤법 검사 |

## [실습 2: PDCA 전체 플로우 체험] 65:00~1:20:00

### 발화문 -- PDCA 개념 소개 (65:00~1:07:00)

> 자, 실습 두 번째. 오늘의 메인 이벤트입니다.
>
> bkit의 핵심 워크플로우인 PDCA를 직접 체험해볼 거예요.
>
> PDCA. Plan, Design, Do, Check, Act. 기획, 설계, 구현, 검증, 개선. 다섯 단계예요.
>
> [화면: PDCA 다이어그램]
>
> ```
> Plan (기획) → Design (설계) → Do (구현) → Check (검증) → Act (개선)
> "뭘 만들지?"    "어떻게 만들지?"   "만들자!"    "잘 됐나?"    "더 좋게!"
> ```
>
> 이거 기자분들한테 친숙하지 않나요? 취재 기획 세우고, 구성 잡고, 기사 쓰고, 교열 보고, 수정 반영. 같은 순서예요.
>
> 지금까지 바이브코딩에서 "만들어줘" 하면 AI가 바로 코드를 짰잖아요. 그건 PDCA 중에 Do만 한 거예요. 기획도 없이, 설계도 없이, 검증도 없이, 바로 만든 거. 당연히 품질이 들쭉날쭉하죠.
>
> bkit의 PDCA는 이 다섯 단계를 체계적으로 밟아요. 그리고 각 단계에서 에이전트들이 역할을 나눠서 일해요.
>
> 직접 해봅시다. 2주차에 만든 프로젝트에 기능 하나를 추가해볼 거예요.
>
> 추가할 기능은 "검색 기록 저장 기능"이에요. 뉴스 대시보드에서 키워드를 검색하면, 검색한 기록이 남는 기능. 간단하지만 PDCA를 체험하기에 딱 좋아요.

### 발화문 -- Step 1: Plan (1:02:00~1:05:00)

> [화면: 강사의 VS Code 터미널. Claude Code 실행 중]
>
> 자, Claude Code가 실행된 상태에서, 이렇게 입력합니다.
>
> "검색 기록 저장 기능 추가해줘"
>
> [수강생 실습: Claude Code에서 "검색 기록 저장 기능 추가해줘" 입력]
>
> 프로젝트가 없으신 분은, "간단한 메모장 앱을 만들어줘. 메모를 추가하고 삭제할 수 있는 웹페이지"라고 입력하세요. 상관없어요, PDCA 흐름을 체험하는 게 목적이니까.
>
> 자, 엔터를 누르면... 여기를 주목하세요.
>
> (잠시 기다리며)
>
> 보이시나요? AI가 바로 코드를 짜기 시작하지 않아요. 먼저 기획서를 쓰고 있어요!
>
> [화면: bkit이 자동 생성하는 Plan 문서를 보여줌]
>
> "이 기능을 추가하려면 이런 것들이 필요합니다." 기능 범위, 필요한 변경사항, 예상 파일 목록. 기획서가 자동으로 만들어지고 있어요.
>
> 이게 Plan 단계예요. "만들어줘"라고 했는데, 먼저 "뭘 만들 건지" 정리부터 하는 거죠.
>
> 이 순간이 오프닝에서 말한 A씨와 B씨의 차이예요. A씨는 "만들어줘" 하면 바로 코드를 짰어요. B씨는 기획서가 먼저 나왔어요. bkit이 B씨처럼 일하게 해주는 거예요.

### 발화문 -- Step 2: Design (1:05:00~1:07:00)

> 기획서가 나오면, 다음은 Design. 설계 단계예요.
>
> AI가 자동으로 설계로 넘어갈 수도 있고, 여러분이 "설계해줘"라고 한마디 더 할 수도 있어요. bkit이 설정에 따라 자동으로 진행하기도 합니다.
>
> [화면: Design 문서가 생성되는 과정]
>
> 설계서를 보세요. "localStorage에 검색어를 저장하고, 사이드바에 히스토리 목록을 표시합니다." 이렇게 구체적인 기술 설계가 나와요.
>
> 기자분들, 기사 쓰기 전에 구성안을 잡잖아요. "리드는 이렇게, 본문은 이런 순서로, 인포그래픽은 여기에." 그것과 같은 거예요. 코드를 짜기 전에 "어떻게 만들지" 설계부터 하는 거죠.

### 발화문 -- Step 3: Do (1:07:00~1:10:00)

> 기획이 끝나고, 설계가 끝났어요. 이제 진짜 만듭니다. Do 단계.
>
> [화면: 실제 코드가 생성되는 과정]
>
> AI가 코드를 짜기 시작했어요. 근데 중요한 건, 이전에는 맥락 없이 그냥 짰지만, 이번에는 기획서와 설계서를 참조하면서 짜고 있다는 거예요. 그러니까 기존 코드와 충돌이 안 나요.
>
> 여기서 CLAUDE.md가 힘을 발휘해요. "한 번에 하나만 수정해줘", "기존 기능 깨지지 않게 해줘" 같은 규칙이 적혀 있으니까, AI가 그 규칙을 지키면서 코드를 작성해요.
>
> (코드가 생성된 후)
>
> 됐어요! 브라우저에서 한번 확인해볼까요?
>
> [화면: 브라우저에서 검색 기록 저장 기능이 동작하는 것 확인]
>
> 보이시죠? 검색어를 입력하면 기록이 옆에 남아요. 이걸 AI가 기획서 보고, 설계서 보고, 만든 거예요.

### 발화문 -- Step 4: Check (1:10:00~1:14:00)

> 자, 여기서 끝이 아니에요. 이게 bkit의 진짜 파워입니다. Check 단계.
>
> "확인해줘"라고 해보세요. 또는 bkit이 자동으로 Check 단계를 시작할 수도 있어요.
>
> [수강생 실습: "확인해줘" 입력]
>
> [화면: Match Rate 리포트가 생성되는 과정]
>
> 보이시나요? Match Rate라는 게 나와요. "설계서 대비 구현 일치율: 85%."
>
> 이게 뭐냐면, 아까 설계서에서 "이런 기능을 이렇게 만들겠습니다"라고 계획했잖아요. 그 계획대로 실제로 만들어졌는지 AI가 스스로 검사한 거예요.
>
> 85%라는 건, 대부분은 설계대로 됐는데 뭔가 빠진 게 있다는 뜻이에요. 그리고 그 밑을 보면, "누락 항목: 검색 기록 삭제 버튼"이라고 구체적으로 알려줘요.
>
> 이건 교열 리포트예요. 기사를 쓰고 교열팀에 넘기면, "여기 오타 있어요, 여기 인용 누락이에요"라고 구체적으로 알려주잖아요. 그것과 똑같아요. AI가 스스로 교열하고, 빠진 부분을 찾아낸 겁니다.
>
> 이게 놀라운 거예요. 이전에는 "만들어줘" 하면 끝이었잖아요. 빠진 게 있는지 여러분이 직접 찾아야 했어요. 근데 이제 AI가 "85%요. 삭제 버튼이 빠졌어요"라고 먼저 알려줘요.

### 발화문 -- Step 5: Act (1:14:00~1:18:00)

> 마지막 단계. Act. 개선.
>
> "개선해줘"라고 하면, AI가 누락 항목을 자동으로 보완해요.
>
> [수강생 실습: "개선해줘" 입력]
>
> [화면: Match Rate가 올라가는 과정]
>
> 보세요. 삭제 버튼이 추가됐어요. 그리고 Match Rate가 올라갔어요. 85%에서 92%로. 또 한 번 더 돌리면 더 올라갈 수도 있어요. bkit은 최대 5번까지 자동으로 반복해요.
>
> 85에서 92로 올라가는 게 눈에 보이니까 신뢰가 가죠? "아, AI가 정말 검증하고 개선하고 있구나."
>
> [화면: 최종 완료 화면. 브라우저에서 검색 기록 저장 + 삭제까지 되는 것 확인]
>
> 자, 방금 뭘 한 거냐면요.
>
> "기능 추가해줘" 한마디에, AI가 기획서를 만들고, 설계를 하고, 코드를 짜고, 스스로 검증하고, 빠진 부분을 찾아서 보완했어요. Plan, Design, Do, Check, Act. 다섯 단계를 체계적으로 밟은 거예요.
>
> 오프닝의 B씨가 1시간 만에 끝낸 비결이 이겁니다. AI가 기획부터 검증까지 체계적으로 일하니까 충돌도 안 나고, 빠진 것도 잡아내고, 품질이 확보되는 거예요.
>
